# 面试讲解指南

这个文档帮你把 RAGLab 讲成一次"加分项"：先讲整体，再按面试官的兴趣深入，最后主动抛出局限与下一步。

## 30 秒电梯陈述

> 我做了一个评测驱动的 RAG + Agent 项目。它不依赖任何检索库：BM25 是我自己实现的，向量检索基于 NumPy，混合检索用 RRF 融合；生成端带引用溯源；最核心的是我内置了一套评测体系，把检索质量（MRR、命中率）和答案质量（忠实度、相关性）量化，生成可复现的报告。代码全部有单元测试，CI 里用 mock 模式离线跑通，接 DeepSeek/Qwen 或本地 Ollama 都能跑。

## 高频追问与参考答案

### Q1：BM25 和向量检索各有什么优缺点？为什么需要混合？

- BM25：词法匹配，精确但无法处理同义改写；对专有名词、编号（如型号、工号）效果好。
- 向量：语义匹配，能处理同义，但可能漏掉字面完全一致的片段（Embedding 会丢失词面信息）。
- 混合 + RRF：两者取长补短，RRF 只看排名，避免分数量纲问题。

### Q2：你的分块策略是什么？为什么 chunk 大小影响效果？

- 提供固定长度、递归字符、Markdown 标题感知三种，默认递归切分。
- chunk 太小：上下文碎片化、引用信息不足；太大：检索命中噪声多、浪费上下文窗口。
- 针对中文，我会在句号/分号处优先切分，尽量不切断语义。

### Q3：如何评测"回答得好不好"？

- 检索层：hit_rate@k、MRR、precision@k，离线可算。
- 答案层：faithfulness（是否忠于上下文）和 answer_relevance（是否切题），用 LLM-as-judge。
- 设计原则：先离线后裁判；裁判 prompt 只输出分值，便于解析与复现；评测集可沉淀为回归门禁。

### Q4：怎么避免 LLM 幻觉？

- 生成 prompt 强制"只依据上下文回答，找不到就明说"。
- 引用机制：回答必须标注 `[n]`，事后可追溯到 chunk，可校验。
- 评测兜底：faithfulness 指标持续监控，低于阈值触发告警或降级。

### Q5：ReAct Agent 的原理？

- 循环执行 Thought（思考）→ Action（选工具）→ Observation（观察结果），最多 N 轮。
- 工具用 JSON Schema 描述，方便 LLM 生成结构化调用参数。
- 关键工程点：解析要稳健（正则 + JSON 容错）、限制迭代次数防死循环、记录完整 trace。

### Q6：如果数据量到千万级，哪里会先撑不住？怎么改？

- BM25：内存倒排索引 → 换 ES/OpenSearch。
- 向量：NumPy 内存暴力搜索 → 换 FAISS（IVF/HNSW）/ Milvus / pgvector。
- SQLite 元数据 → PostgreSQL。
- 检索：加一级粗排（embedding recall）再精排（rerank）的两段式，控制候选集大小。

### Q7：这个项目和 Bisheng / Dify 这些平台的区别？

- 它们追求功能全面（工作流编排、多租户、权限），代码规模大。
- RAGLab 刻意做减法：把 RAG 主链路 + 评测闭环做深、做透，代码量小到可以逐行讲清。
- 借鉴了它们"评测中心 + 可观测 + 可插拔模型"的设计思想，但每个模块都是自己实现的。

## 演示脚本（建议 5 分钟）

1. `raglab ingest examples/data/buaa.md`：展示摄入。
2. `raglab query "北航的校训是什么？"`：展示带引用的回答。
3. `raglab eval-dataset examples/eval_dataset.json`：展示评测报告（先 mock，再换真实模型对比）。
4. 打开 `http://127.0.0.1:8000/docs`：展示 API 设计与 OpenAPI。
5. 展示 GitHub Actions 绿勾：CI 自动跑 lint + 测试 + 冒烟。

## 主动暴露的局限（加分项）

- 向量检索是内存版，大数据量需换 FAISS/Milvus。
- LLM 裁判存在自评偏差，可引入多裁判投票或人工标注集校准。
- 尚未做查询改写/多路召回等高级检索，这是明确的下一步。
